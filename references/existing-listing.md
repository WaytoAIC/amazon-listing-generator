# 改旧稿：一次性优化和复盘迭代

用户给了现有 Listing 时读。两种情况共用第一步，然后分开走。

## 第一步：体检

1. 把现有内容填进 existing_listing：标题、Item Highlights、五点、描述、Search Terms、后台属性、图片信息、A+。
2. 把现有文案按交付模板的标题格式排好，存成 `listing-<商品英文简称>-<站点>-旧稿.md`，放在用户的工作目录，留着做对照。只放旧文案的几个小节，别的不用加，脚本会自己在末尾加「机器检查结果」。先跑一遍检查脚本（用法见 modules/31-compliance-check.md 的“跑脚本”），拿到客观的问题清单。
3. 用户只给了部分旧稿时，脚本只查给到的部分；这时“五点不足三条”之类的报错说明的是资料不全，不是旧稿违规。
4. 列缺口：标题是否超长、有没有 Item Highlights、事实不完整、关键词缺口、前两条五点不够转化、必答问题答不上、前后台打架、潜在违规。必答问题这一项，用用户给的问题和评论里的疑问粗看即可，不必先建完整的必答问题表；用户点名要做问答覆盖验证时除外，那时按 modules/30-alexa-coverage-check.md 建完整的表。
5. 先给结论和改写优先级，再动手。结论写进交付模板的「体检结论」，同时在对话里说。

## 只检查、先不改

用户说先不要改文案时：只出旧稿这一个文件，检查用到的表和「体检结论」都写在它里面；不补写，不重跑。脚本报的不通过项和旧文案回答了没依据的问题，都是要报告的发现，不是要你去修的东西。

## 情况一：一次性优化（没有上线后的数据）

- 只改用户点名的模块；没点名就按优先级给建议，等用户选。标题和 Item Highlights 算同一个模块：用户只点了标题，也一并给出 Item Highlights，并说明旧标题放不下的信息要有去处。
- 交付文件只放这次改的模块，旧文案不抄进来；旧文案的问题写在「体检结论」里。
- 这一轮放不下、又该去别的模块的信息（比如该进 Search Terms 的词），在「体检结论」里列出来，留给下一轮。
- 旧标题超长：先做关键词四层分配，再拆成“合规标题 + Item Highlights”，信息尽量不丢。
- 改 Search Terms 前，先重新列出标题、Item Highlights、五点里已用的词。
- 保留旧稿里还有效的信息，不为改而改。

## 情况二：复盘迭代（有 performance_data 或 iteration_log）

1. 先定位问题出在哪一段，再决定改哪个模块：

   | 现象 | 先看哪些模块 |
   |---|---|
   | 曝光低 | 标题、Search Terms、后台属性 |
   | 曝光够，点击率低 | 主图、标题 |
   | 点击够，转化率低 | 五点、图片、A+、视频 |
   | 退货多、差评集中 | “适合谁、不适合谁”的说明，参数是否写清，图片有没有让人误会 |

2. 一轮最多改 2 个模块，其余排队，并把排队顺序告诉用户。这样数据变化才能算到具体改动头上。用户要求全部重写时，说明原因，给出排队顺序，不照做。
3. 合规问题优先修。同一个合规问题牵涉多个模块时，算一次修复，牵涉到的地方都要改，不受 2 个模块限制；但这一轮不再叠加别的优化。在记录里注明“本轮含合规修复，效果归因会受影响”。
4. 距上次改动不到 2 到 4 周、数据还不够比较时，提醒用户先等，不叠加新改动；合规修复不用等。
5. 退货和差评说明的是“买家遇到了什么”：可以据此把限制和不适合的情况写清楚（比如不能进洗碗机），但不能据此宣称相反的功能（不能因为差评说漏，就写不漏）。
6. 改哪个模块，就按 intake-schema.md 的表补做那个模块的准备步骤；检查规则和单模块任务一样。图片只重写有问题的图位。
7. 每轮写一行迭代记录：问题、证据、改了什么、假设、看哪个指标、复查日期。
8. 上一轮「上架前待办」里已经办完的事项，是这一轮的新输入。

## 产出

「体检结论」，加被改模块的新文案（仍用交付模板）；复盘迭代时再加「迭代记录」。
