# 改旧稿：一次性优化和复盘迭代

用户给了现有 Listing 时读。两种情况共用第一步，然后分开走。

## 第一步：体检

1. 把现有内容填进 existing_listing：标题、Item Highlights、五点、描述、Search Terms、后台属性、图片信息、A+。
2. 把现有文案按交付模板的标题格式排好，先跑一遍检查脚本，拿到客观的问题清单。
3. 列缺口：标题是否超长、有没有 Item Highlights、事实不完整、关键词缺口、前两条五点不够转化、必答问题答不上、前后台打架、潜在违规。
4. 先给结论和改写优先级，再动手。

## 情况一：一次性优化（没有上线后的数据）

- 只改用户点名的模块；没点名就按优先级给建议，等用户选。
- 旧标题超长：先做关键词四层分配，再拆成“合规标题 + Item Highlights”，信息尽量不丢。
- 改 Search Terms 前，先重新列出标题、Item Highlights、五点里已用的词。
- 保留旧稿里还有效的信息，不为改而改。

## 情况二：复盘迭代（有 performance_data 或 iteration_log）

1. 先定位问题出在哪一段，再决定改哪个模块：

   | 现象 | 先看哪些模块 |
   |---|---|
   | 曝光低 | 标题、Search Terms、后台属性 |
   | 曝光够，点击率低 | 主图、标题 |
   | 点击够，转化率低 | 五点、图片、A+、视频 |
   | 退货多、差评集中 | “适合谁、不适合谁”的说明，参数是否写清，图片有没有让人误会 |

2. 一轮最多改 2 个模块，其余排队。这样数据变化才能算到具体改动头上。用户要求全部重写时，说明原因，给出排队顺序，不照做。
3. 合规问题优先修，并且占用本轮名额；在记录里注明“本轮含合规修复，效果归因会受影响”。
4. 距上次改动太近、数据还没稳定时，提醒用户先等，不叠加新改动。
5. 每轮写一行迭代记录：问题、证据、改了什么、假设、看哪个指标、复查日期。
6. 上一轮「上架前待办」里已经办完的事项，是这一轮的新输入。

## 产出

体检结论，加被改模块的新文案（仍用交付模板）；复盘迭代时再加「迭代记录」。
