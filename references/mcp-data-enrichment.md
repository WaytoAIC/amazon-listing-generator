# MCP Data Enrichment

## 目的

当系统接了 Sorftime、卖家精灵或其他 Amazon 数据 MCP 时，不要只依赖用户手写资料。先把可自动拉到的关键词、竞品、评论、类目和商品详情补齐，再进入 Listing 起草。

## 何时触发

以下任一情况成立，就优先做 MCP 数据补强：

- 用户明确要求“数据驱动”“结合市场数据”“参考竞品数据”
- 用户没给关键词池，或关键词池明显过短、过粗
- 用户没给竞品结论，但要求标题、图片、A+ 更贴近市场打法
- 用户没给评论总结，但要求五点、必答问题、A+ 更贴近真实痛点
- 用户提供的是一个 ASIN、类目、关键词或竞品链接，希望你反推 Listing

## 数据来源优先级

从高到低：

1. 用户提供的官方资料、包装清单、品牌说明、认证和图片
2. 用户确认过的商品详情页事实
3. MCP 抓取到的自家产品详情、竞品详情、评论、关键词、类目和市场数据
4. 由 MCP 证据归纳出来的推断性结论

规则：

- 前 2 类可以进入前台事实表述。
- 第 3 类需要先判断是否与用户资料冲突；其中的自家产品数据在用户确认前一律标“待核实”。
- 第 4 类只能用于排序、侧重点和提示，不要直接写成事实。

## 工具选择建议

### Sorftime 更适合做什么

- `product_detail`
  - 补产品基础信息、标题、价格、评分、类目、变体
- `product_reviews`
  - 抽高频负评、正评、误用和兼容性抱怨
- `keyword_detail`
  - 看单词热度、趋势和搜索量基础面
- `keyword_extends`
  - 拉长尾词、场景词、需求词
- `competitor_product_keywords`
  - 看竞品在核心词下的自然曝光能力
- `product_traffic_terms`
  - 反查产品近期在哪些关键词前 3 页有曝光
- `category_keywords`
  - 看类目主词与语义带
- `category_report` / `category_trend`
  - 做类目结构和趋势判断

### 卖家精灵更适合做什么

- `asin_detail` / `asin_detail_with_coupon_trend`
  - 补商品属性、促销、评分、卖家和配送信息
- `review`
  - 看评论内容、集中痛点和用户评价倾向
- `traffic_keyword`
  - 看 ASIN 的自然词、广告词和流量占比词
- `traffic_source`
  - 看 ASIN 或关键词的流量来源结构
- `keyword_miner`
  - 批量筛高价值关键词、长尾词和竞争度
- `keyword_order`
  - 判断转化优质词、平稳词、流失词和无效曝光词
- `competitor_lookup`
  - 拉竞品清单、销量、价格、评分和卖家结构
- `market_research` / `market_research_statistics`
  - 做类目、竞争度、品牌集中度和新品机会判断

## 推荐补强顺序

### 1. 自家产品与竞品基础面

先拿这些信息：

- 自家产品标题、类目、价格、评分、变体、基础属性
- 3 到 5 个竞品的标题、价格带、评分和类目位置
- 竞品前台第一眼强调的点

输出到这些字段：

- `product_name`
- `category_term`
- `market_positioning.category`
- `market_positioning.price_band`
- `competitor_insights`
- `market_positioning.competitor_patterns`

### 2. 关键词与词路

重点补这些：

- 主词
- 高价值转化词
- 长尾词
- 兼容词
- 场景词
- 问题词

输出到这些字段：

- `keyword_pool.core`
- `keyword_pool.secondary`
- `keyword_pool.long_tail`
- `semantic_buckets`

每条关键词可以带上热度和出处。关键词补完后，先做关键词四层分配（见 modules/02-keyword-allocation.md），再进入起草。

### 3. 评论与痛点

重点抽这些：

- 高频差评原因
- 正评中最常被提到的购买理由
- 用户误用场景
- 兼容或安装相关抱怨

输出到这些字段：

- `review_insights.pains`
- `review_insights.expectations`
- `review_insights.misuse`
- `buyer_questions`（评论和问答里买家反复问的问题，是必答问题表的来源）

每条洞察可以带上出处，方便回溯。

### 4. 类目和定位

重点补这些：

- 当前价格带属于低、中还是中高端
- 市场主流沟通方式是什么
- 哪些卖点是行业标配，哪些才是差异点

输出到这些字段：

- `brand_tone`
- `market_positioning`
- `competitor_insights`

## 模块映射

| 模块 | 优先使用的数据 |
|---|---|
| 关键词四层分配（前置步骤） | 关键词热度与流量数据、类目主词、竞品流量词 |
| 标题 | 核心产品词、竞品标题前半段、类目主词、价格带定位 |
| Item Highlights | 功能属性词、材质词；竞品常写、自家也确实具备但标题放不下的属性 |
| 五点 | 评论痛点、用户期待、兼容风险、使用场景词和购买理由词 |
| Search Terms | 流量词、长尾词、同义词、未覆盖语义、拼写变体 |
| 图片需求单 | 竞品前 3 张图打法、评论痛点、场景词 |
| A+ 需求单 | 市场定位、用户场景、评论期待、竞品差异化结构 |
| 视频分镜表 | 场景词、评论痛点、竞品演示逻辑、转化词 |
| 必答问题表、Alexa 问答覆盖验证 | 评论和问答里的疑问、兼容风险、安装误解、流量词里的问题意图 |
| 后台属性表 | 竞品填了哪些属性，只作参考，值必须来自自家事实 |
| 合规检查 | 前后台一致性、是否把推断写成事实、是否遗漏高频问题 |
| 复盘迭代 | 关键词排名、流量词和流量来源的变化 |

## 安全边界

- 不要把 MCP 的销量、BSR、PPC、评论量、增长率直接写进标题、Item Highlights、五点、A+ 或图片文案。
- 不要因为竞品写了某个参数，就自动假设自家产品也有。
- 不要把评论中的个别用户表述写成稳定结论，除非有反复出现的证据。
- 如果 MCP 抓到的自家商品标题或详情页本身可能有错误，不要直接复制进新文案，先与用户给的资料对照。

## 最小可行输出

如果 MCP 可用但时间有限，至少补强以下 4 项再写 Listing：

1. 关键词主词和长尾词
2. 3 个竞品的第一眼信息结构
3. 高频评论痛点和误用
4. 兼容风险或限制条件
